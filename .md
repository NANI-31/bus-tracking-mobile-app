## Detailed Topic breakdowns

### Topic 1: Python Fundamentals

- **Phase / Schedule:** Phase 1 | Month 1 | The Reasoning Layer
- **Subtopics:** Reading code (not just writing) • Code comprehension & debugging • Best practices & organization

#### The Five Laws Framework

- **Law 1: Prediction Before Explanation**
  - _Prediction:_ "I think Python is just about writing scripts. I think it fails when you need performance."
  - _Correction:_ Python is about READING code — understanding others' codebases, debugging production issues. AI writes code; you must READ and JUDGE it. The real skill is comprehension, not generation.
- **Law 2: Failure Modes Over Features**
  - _Why Invented:_ Created 1991 by Guido van Rossum to replace Perl's complexity with readability ("There should be one obvious way to do it").
  - _Quiet Assumptions:_ Dynamic typing is fine for your scale • Memory management is handled • GIL won't bottleneck you • Libraries exist for your use case.
  - _Silent Failures:_ Memory leaks from circular references • GIL blocking parallel CPU work • Type errors caught only at runtime in production • Import-time side effects breaking deployments.
  - _Replacements:_ Cython/Numba for performance paths • Type hints + `mypy` for safety • Rust/C extensions for CPU-bound work • Multiprocessing to bypass GIL.
- **Law 3: Compression Beats Coverage**
  - _Mastery Strategy:_ Master reading ONE complex codebase (e.g., FastAPI source). Once you navigate real production code, every Python project becomes readable.
- **Law 4: Emotion Creates Judgment**
  - _Engineer Stakes:_ Take someone's buggy production code and fix it under a 2-hour deadline. Post: _"Spent 2 hours debugging a memory leak in a Flask app. Root cause: circular reference in caching decorator."_
- **Law 5: AI Accelerates, Humans Judge**
  - _Humans Own:_ What's the right abstraction level? Is this code maintainable? Should we refactor or ship?
  - _AI Handles:_ Syntax generation, boilerplate code, translating between styles, docstrings, test cases.

### Topic 2: NumPy

- **Phase / Schedule:** Phase 1 | Month 1 | The Reasoning Layer
- **Subtopics:** Array thinking vs iteration • Vectorization • Broadcasting • Memory efficiency • Universal functions

#### The Five Laws Framework

- **Law 1: Prediction Before Explanation**
  - _Prediction:_ "I think NumPy is just a faster way to do math on lists. I think it fails with very large datasets."
  - _Correction:_ NumPy requires a MENTAL MODEL SHIFT — from iteration to array thinking. It's not 'faster loops' — it's eliminating loops entirely. Broadcasting operates on mismatched shapes without copying data.
- **Law 2: Failure Modes Over Features**
  - _Why Invented:_ Created 2005 (from Numeric 1995). Scientists needed fast numerical computation in Python without writing C.
  - _Quiet Assumptions:_ Data fits in memory • Operations are element-wise or matrix-based • Homogeneous data types • Contiguous memory layout.
  - _Silent Failures:_ Broadcasting producing wrong-shaped results silently • Memory explosion from unintended copies (view vs copy) • `dtype` overflow • Non-contiguous arrays killing performance.
  - _Replacements:_ Dask for out-of-memory • CuPy for GPU • JAX for autodiff • Sparse arrays for mostly-zero data.
- **Law 3: Compression Beats Coverage**
  - _Mastery Strategy:_ Master vectorization and broadcasting deeply. Once you think in arrays, Pandas, PyTorch tensors, and SQL aggregations all feel like the same pattern.
- **Law 4: Emotion Creates Judgment**
  - _Engineer Stakes:_ Benchmark a loop version vs a vectorized version on a real dataset. Post: _"My loop took 45 seconds. Vectorized: 0.3 seconds. 150x speedup."_
- **Law 5: AI Accelerates, Humans Judge**
  - _Humans Own:_ When to vectorize vs when readability matters more. When to use views vs copies.
  - _AI Handles:_ Vectorized equivalents of loops, broadcasting rule explanations, `dtype` conversions.

### Topic 3: Pandas

- **Phase / Schedule:** Phase 1 | Month 1 | The Reasoning Layer
- **Subtopics:** DataFrame operations • Data manipulation • Performance optimization • Real-world data cleaning • GroupBy & merge

#### The Five Laws Framework

- **Law 1: Prediction Before Explanation**
  - _Prediction:_ "I think Pandas is Excel for Python. I think it fails with big data."
  - _Correction:_ Pandas is about THINKING IN DATAFRAMES — not row-by-row iteration. It fails with MESSY data: missing values, mixed types, inconsistent formats. 80% of ML work is data cleaning in Pandas.
- **Law 2: Failure Modes Over Features**
  - _Why Invented:_ Created 2008 by Wes McKinney at AQR Capital. Finance needed R's `data.frame` in Python.
  - _Quiet Assumptions:_ Data fits in memory • Column types are consistent • Index is meaningful • Operations are column-wise.
  - _Silent Failures:_ `SettingWithCopyWarning` hiding bugs • Chained indexing creating copies not views • `.apply()` being 100x slower than vectorized ops • Silently dropping data on merge mismatches.
  - _Replacements:_ Polars for faster DataFrames • Dask for out-of-memory • PySpark for distributed • DuckDB for SQL analytics.
- **Law 3: Compression Beats Coverage**
  - _Mastery Strategy:_ Master `GroupBy` + `merge` + method chaining (`.groupby().agg().merge().pipe()`).
- **Law 4: Emotion Creates Judgment**
  - _Engineer Stakes:_ Clean a real, messy CSV with mixed date formats and 30% missing values under time constraints.
- **Law 5: AI Accelerates, Humans Judge**
  - _Humans Own:_ What constitutes 'clean' data? How to handle missing values (drop, impute, or flag)?
  - _AI Handles:_ Cleaning pipelines, regex patterns, optimizing slow Pandas code, Pandas/SQL conversion.

### Topic 5: Linear Algebra

- **Phase / Schedule:** Phase 1 | Month 1 | The Reasoning Layer
- **Subtopics:** Geometric intuition • Matrix operations • Vector spaces • Eigenvalues/eigenvectors • SVD • ML applications

#### The Five Laws Framework

- **Law 1: Prediction Before Explanation**
  - _Prediction:_ "I think Linear Algebra is about solving equations with matrices. I think it's theoretical for ML."
  - _Correction:_ Linear Algebra is GEOMETRIC INTUITION — matrices are transformations of space. Eigenvalues = how space stretches. SVD = rotate → stretch → rotate. This explains why PCA and embeddings work.
- **Law 2: Failure Modes Over Features**
  - _Why Invented:_ Formalized in the 1800s. In ML, neural networks ARE matrix multiplications, PCA IS eigendecomposition.
  - _Quiet Assumptions:_ Linearity holds • Matrix is well-conditioned • Numerical precision is sufficient.
  - _Silent Failures:_ Ill-conditioned matrices producing garbage silently • Numerical instability in eigenvalues • Curse of dimensionality breaking distances.
  - _Replacements:_ Iterative methods for large matrices • Sparse representations • Randomized approximate SVD.
- **Law 3: Compression Beats Coverage**
  - _Mastery Strategy:_ Master matrix multiplication as geometric transformation.
- **Law 4: Emotion Creates Judgment**
  - _Engineer Stakes:_ Visualize transformations in 2D/3D and build an interactive notebook explaining eigenvectors geometrically.
- **Law 5: AI Accelerates, Humans Judge**
  - _Humans Own:_ Knowing when geometric intuition outweighs formulas; choosing rank approximations.
  - _AI Handles:_ Matrix computations, eigenvalue decomposition, proofs, matrix visualizations.

- **Law 2: Failure Modes Over Features**

  - _Replacements:_ Gradient clipping • Skip connections (ResNet) • Adam optimizer • Gradient-free optimization.

### Topic 7: Linear Regression (Compression Anchor)

- **Phase / Schedule:** Phase 1 | Month 2 | Classical ML
- **Subtopics:** Mathematical foundations • Assumptions & violations • Failure modes • Cost functions • Regularization (Ridge/Lasso) • Residual analysis

#### The Five Laws Framework

- **Law 1: Prediction Before Explanation**
  - _Prediction:_ "I think it draws a line through data for simple linear relationships."
  - _Correction:_ Minimizes SQUARED distances — penalizing large errors heavily. With feature engineering, it models complex patterns. Fails SILENTLY when assumptions like homoscedasticity or no multicollinearity are violated.
- **Law 2: Failure Modes Over Features**
  - _Why Invented:_ Gauss (1800s) to predict planetary orbits from noisy telescope data.
  - _Quiet Assumptions:_ Linearity • Independence of errors • Homoscedasticity • Normality of errors • No multicollinearity.
  - _Silent Failures:_ Data drift • Outliers distorting the slope • Extrapolation beyond train bounds • Feature leakage.
  - _Replacements:_ Robust regression (Huber) for outliers • Ridge/Lasso for multicollinearity • Tree models for non-linear interactions.
- **Law 3: Compression Beats Coverage**
  - _Mastery Strategy:_ Treat this topic as your COMPRESSION ANCHOR (spend 3 weeks here). Logistic regression, Ridge, Lasso, Polynomial features are all variations of this core model.
- **Law 4: Emotion Creates Judgment**
  - _Engineer Stakes:_ Build a model with 95% accuracy, deploy it, discover feature leakage in production, and document the root cause.
- **Law 5: AI Accelerates, Humans Judge**
  - _Humans Own:_ Assessing assumption violations, selecting regularization strength, evaluating business interpretability tradeoffs.
  - _AI Handles:_ Residual plots, assumption testing scripts, cross-validation boilerplate.

### Topic 8: Logistic Regression

- **Phase / Schedule:** Phase 1 | Month 2 | Classical ML
- **Subtopics:** Link functions • Binary/multi-class • Decision boundaries • Sigmoid derivation • Threshold selection • Calibration

#### The Five Laws Framework

- **Law 1: Prediction Before Explanation**
  - _Prediction:_ "I think it's Linear Regression for classification by adding a sigmoid."
  - _Correction:_ Models the LOG-ODDS of class membership. Sigmoid squashes predictions into [0,1] probabilities. Crucially provides CALIBRATED probabilities, making threshold selection a strategic business choice.
- **Law 2: Failure Modes Over Features**
  - _Why Invented:_ Unbounded outputs of linear models fail for probabilities; logistic functions bound outputs naturally to [0,1].
  - _Quiet Assumptions:_ Linear decision boundary in log-odds • Class independence • No severe class imbalance.
  - _Silent Failures:_ Probability calibration drift • High accuracy mask under class imbalance (e.g., 99% accuracy by predicting majority class).
  - _Replacements:_ SVM/Trees for non-linear boundaries • SMOTE/Class weighting for imbalance • Platt scaling for calibration.
- **Law 3: Compression Beats Coverage**
  - _Mastery Strategy:_ Connect directly to Linear Regression: same core math + logit link + cross-entropy loss.
- **Law 4: Emotion Creates Judgment**
  - _Engineer Stakes:_ Build a spam filter and tune prediction thresholds directly against false positive/negative trade-offs.
- **Law 5: AI Accelerates, Humans Judge**
  - _Humans Own:_ Setting decision thresholds based on business risk; choosing precision vs. recall priorities.
  - _AI Handles:_ Sigmoid derivations, ROC/AUC curve generation, calibration plots.

### Topic 9: Decision Trees

- **Phase / Schedule:** Phase 1 | Month 2 | Classical ML
- **Subtopics:** Splitting criteria (Gini, Entropy) • Pruning • Overfitting prevention • Interpretability • Feature importance

#### The Five Laws Framework

- **Law 1: Prediction Before Explanation**
  - _Prediction:_ "I think they split data like a flowchart and fail by overfitting."
  - _Correction:_ Trees are GREEDY and LOCALLY optimal — making the best split at each step, not overall. They overfit by memorizing noise, but require no feature scaling and handle mixed types effortlessly.
- **Law 2: Failure Modes Over Features**
  - _Why Invented:_ Breiman et al. (1984, CART) to provide interpretable models for decision-makers.
  - _Quiet Assumptions:_ Axis-aligned splits are sufficient • Greedy splits approximate optimal global structure.
  - _Silent Failures:_ Severe overfitting on deep trees • High instability (small data changes cause radically different trees) • Bias towards high-cardinality features.
  - _Replacements:_ Random Forests / Pruning for overfitting • Gradient Boosting for high accuracy • Linear models for extrapolation.
- **Law 3: Compression Beats Coverage**
  - _Mastery Strategy:_ Decision trees are the building blocks for ALL ensemble tree methods (Random Forests = bagging; Gradient Boosting = sequential error correction).
- **Law 4: Emotion Creates Judgment**
  - _Engineer Stakes:_ Train an unpruned tree to 100% training accuracy / 60% test accuracy, then systematically prune it.
- **Law 5: AI Accelerates, Humans Judge**
  - _Humans Own:_ Deciding max depth vs. interpretability requirements; choosing when to prune vs. ensemble.
  - _AI Handles:_ Tree visualization diagrams, grid search routines, feature importance plots.

### Topic 10: Random Forests

- **Phase / Schedule:** Phase 1 | Month 2 | Classical ML
- **Subtopics:** Ensemble methods • Bagging • Feature importance • Out-of-bag error • Feature subsampling

#### The Five Laws Framework

- **Law 1: Prediction Before Explanation**
  - _Prediction:_ "I think they are many decision trees averaged together, always beating single trees."
  - _Correction:_ Succeeds through DECORRELATION — randomly subsampling features ensures diverse trees. Out-Of-Bag (OOB) error gives free cross-validation. Struggles with extrapolation and high-dimensional sparse data.
- **Law 2: Failure Modes Over Features**
  - _Why Invented:_ Breiman (2001) to solve decision tree instability via bagging + feature randomization.
  - _Quiet Assumptions:_ Subsampling decorrelates trees sufficiently • Averaging reduces variance without increasing bias significantly.
  - _Silent Failures:_ Biased feature importance on high-cardinality columns • Slow inference latency at scale • Inability to extrapolate trends.
  - _Replacements:_ XGBoost/LightGBM for speed and precision • Linear models for extrapolation.
- **Law 3: Compression Beats Coverage**
  - _Mastery Strategy:_ Random Forests = Bagging + Feature Subsampling. Understand the general principle of combining weak, uncorrelated learners.
- **Law 4: Emotion Creates Judgment**
  - _Engineer Stakes:_ Compare 1, 10, 100, and 1000 trees on a dataset to plot where diminishing returns occur in real time.
- **Law 5: AI Accelerates, Humans Judge**
  - _Humans Own:_ Balancing tree count vs. inference latency budget; evaluating feature importance metrics.
  - _AI Handles:_ Hyperparameter search, OOB scoring scripts, parallelization configs.

### Topic 11: Gradient Boosting (XGBoost, LightGBM, CatBoost)

- **Phase / Schedule:** Phase 1 | Month 2 | Classical ML
- **Subtopics:** Sequential trees • XGBoost • LightGBM • CatBoost • Silent failures • Hyperparameter tuning

#### The Five Laws Framework

- **Law 1: Prediction Before Explanation**
  - _Prediction:_ "I think it's like Random Forests but sequential, and XGBoost always wins on tabular data."
  - _Correction:_ Builds trees sequentially to correct prior residual errors (gradient descent in function space). XGBoost adds explicit regularization. LightGBM uses histogram binning for speed. CatBoost natively handles categorical features.
- **Law 2: Failure Modes Over Features**
  - _Why Invented:_ Friedman (2001); XGBoost by Tianqi Chen (2016). Designed to reduce both bias and variance on tabular data.
  - _Quiet Assumptions:_ Production data distribution matches training data • Hyperparameters are properly tuned.
  - _Silent Failures:_ Degradation under distribution drift • Overfitting on noisy labels • High sensitivity to hyperparameter choices.
  - _Replacements:_ Deep learning / Transformers for unstructured data • Simple linear models when low latency or strict interpretability is paramount.
- **Law 3: Compression Beats Coverage**
  - _Mastery Strategy:_ Understand boosting as sequential residual fitting. The algorithmic engine is identical across XGBoost, LightGBM, and CatBoost — the differences lie in speed, binning, and categorical handling optimizations.
- **Law 4: Emotion Creates Judgment**
  - _Engineer Stakes:_ Tune XGBoost against LightGBM and CatBoost on a real dataset, benchmarking training time, memory footprint, and inference latency.
- **Law 5: AI Accelerates, Humans Judge**
  - _Humans Own:_ Choosing between XGBoost/LightGBM/CatBoost based on system constraints; monitoring drift in production.
  - _AI Handles:_ Bayesian hyperparameter optimization scripts, metric logging, comparative benchmarking code.
